# Evidence Pattern Coverage Research

Date: 2026-07-24

## Executive Summary

Verdict: the proposed taxonomy is sufficient as an evidence-discovery accelerator, but not sufficient as a full repository-to-Kubernetes analyzer. Official ecosystem docs show many stable files and keys that can be extracted deterministically: `pom.xml`, `build.gradle`, `package.json`, `pyproject.toml`, `go.mod`, `*.csproj`, `Gemfile`, `composer.json`, `Cargo.toml`, `Dockerfile`, Compose files, Kubernetes manifests, Helm charts, Kustomize overlays, and GitHub Actions workflows. These formats are documented by their owning projects and can safely produce typed evidence with source lines: build metadata, dependency declarations, scripts, images, ports, probes, environment-variable names, and deployment-resource shape.

The taxonomy is not sufficient as a full analyzer because Kubernetes migration readiness depends on semantic judgments that official file formats do not encode: whether a script is production startup or local development, whether a dependency declaration is actually used at runtime, whether a component is deployable or a library, whether a Compose service is production or local support, and whether a Kubernetes overlay is the default production path. The local validation corpus reached the same result: component identity was stable across eight repositories, but Single/Mono/MSA structure was not explicitly classified in any of 16 runs, output validation failed in all 16 runs, and default/optional role selection was inconsistent in the larger MSA case (`validation/skill-coverage-validation-2026-07-23.md`).

The risky part is not missing a few file names. The risky part is letting evidence patterns become hidden judgment rules. Pattern packs should collect candidate facts; LLM-centered triage and reasoning should interpret them; a deterministic verifier should reject unsupported claims, invalid citations, unsafe secret output, and malformed readiness reports.

## Method

I used primary or high-trust sources only: official framework docs, language/package-manager specifications, first-party CLI references, and the local validation corpus. The sources were selected because they own the file formats or runtime commands that a repository evidence collector would parse. Key sources include Maven POM and Wrapper docs, Gradle Java/Application docs, Spring Boot docs, npm/Yarn/pnpm/Next/Vite/Nest docs, Python packaging specs, uv and Poetry docs, pip docs, FastAPI/Django/Celery docs, Go module docs, Microsoft .NET docs, Rails and Laravel docs, Cargo docs, Dockerfile and Compose specs, Kubernetes/Helm/Kustomize docs, GitHub Actions workflow syntax, and official deployment-platform references for gaps such as Heroku Procfile, Fly, Railway, Render, Serverless Framework, Cloud Foundry, Nx, and Terraform.

## Pattern Taxonomy

Universal patterns should scan the whole repository without interpreting it: file inventory, binary/generated/vendor exclusion, line indexing, path/extension hints, common config formats (`yaml`, `json`, `xml`, `toml`, `properties`, `.env.example`), entrypoint-like terms (`main`, `CMD`, `ENTRYPOINT`, `listen`, `server.port`, `PORT`), dependency hints (`jdbc:`, `redis`, `amqp`, `postgres`, `mysql`, `s3`, `kafka`), deployment hints (`image`, `ports`, `containerPort`, `Service`, `Ingress`), and health hints (`health`, `ready`, `live`, `actuator`, `metrics`). Docker documents the exact semantics of `FROM`, `RUN`, `CMD`, `ENTRYPOINT`, `EXPOSE`, and `HEALTHCHECK`, including that `EXPOSE` documents intended listening ports but does not publish them by itself: https://docs.docker.com/reference/dockerfile.

Ecosystem packs should parse stable formats into typed facts, not conclusions. Maven defines `pom.xml` as the POM and documents coordinates, packaging, dependencies, modules, build settings, properties, and profiles: https://maven.apache.org/pom.html. npm, Yarn, and pnpm document `package.json` scripts/workspaces/package-manager metadata and workspace files: https://docs.npmjs.com/files/package.json/, https://yarnpkg.com/configuration/manifest, https://docs.npmjs.com/misc/workspaces/. Python packaging defines `pyproject.toml` `[project]`, `[build-system]`, dependencies, optional dependencies, and scripts: https://packaging.python.org/specifications/declaring-project-metadata/. Kubernetes documents workload, Service, Ingress, and probe fields: https://kubernetes.io/docs/concepts/workloads/, https://kubernetes.io/docs/concepts/services-networking/service/, https://kubernetes.io/docs/concepts/services-networking/ingress/, https://kubernetes.io/docs/concepts/workloads/pods/probes/.

Negative/absence patterns should record scoped absence, not failure: no Dockerfile, no Kubernetes manifest, no publishable image, no health endpoint, no production command, no external DB config. The local corpus showed missing Dockerfiles and missing production metadata were normal findings, not analysis failures (`validation/skill-coverage-validation-2026-07-23.md`).

LLM-discovered hints are the escape hatch for unfamiliar but real files. They should start as triage evidence and only be promoted when repeated across repositories, documented by an owner, line-addressable, and testable.

## Validation Corpus Check

The corpus covers Java, Python, Node, Maven, Gradle, uv, Poetry, pip, npm, yarn, pnpm, single apps, multi-process apps, frontend-only apps, monorepos, and a multi-language MSA (`validation/skill-coverage-validation-2026-07-23.md`). The proposed taxonomy would cover the high-signal files used in all eight repositories: package manifests, lockfiles, Dockerfiles, Compose files, Kubernetes/Kustomize files, runtime entrypoints, environment examples, and CI workflows.

The corpus also shows why coverage is not enough. Repeated successes came from evidence-rich combinations such as manifest plus lockfile plus Dockerfile/deployment plus entrypoint. Repeated failures were semantic or contract-level: no explicit Single/Mono/MSA classification in 16/16 runs, output schema failures in 16/16 runs, invalid citations in one Poetry run, unstable default/optional MSA classification, and blurred boundaries between application components and third-party infrastructure (`validation/skill-coverage-validation-2026-07-23.md`). Pattern packs can reduce file-search time, but they cannot replace LLM-centered role interpretation and deterministic report validation.

## Gap Analysis

Common platform files outside the initial list should enter as LLM-discovered hints first. Heroku `Procfile` defines root-level process types and gives `web` special HTTP-routing semantics: https://devcenter.heroku.com/articles/procfile. Fly `fly.toml` can define build config, env, HTTP services, internal ports, mounts, process groups, and metrics: https://fly.io/docs/reference/configuration/. Railway uses `railway.toml` or `railway.json` for build/deploy config: https://docs.railway.com/config-as-code/reference. Render Blueprints use `render.yaml`: https://render.com/docs/blueprint-spec. Cloud Foundry uses `manifest.yml` with applications, paths, routes, services, commands, processes, and health checks: https://docs.cloudfoundry.org/devguide/deploy-apps/manifest.html and https://docs.cloudfoundry.org/devguide/deploy-apps/manifest-attributes.html. Serverless Framework uses `serverless.yml` functions and events: https://www.serverless.com/framework/docs/providers/aws/guide/events. Nx uses `nx.json`, `project.json`, and package-level `nx` targets; Turborepo uses `turbo.json` tasks over package workspaces, so both matter for JS monorepos: https://nx.dev/docs/reference/project-configuration and https://turbo.wiki/repo/docs/reference/configuration. Terraform files (`*.tf`, `*.tf.json`) are infrastructure declarations evaluated as modules, not necessarily app runtime topology, so they should be scanned for managed services, variables, and outputs but not converted into app components without corroborating evidence: https://developer.hashicorp.com/terraform/language/files and https://developer.hashicorp.com/terraform/language/values/variables.

Makefile and Taskfile are important gaps because many repositories encode build/start/deploy commands there, but target names are conventional rather than semantically guaranteed. GNU Make executes named targets from Makefiles, and Task discovers `Taskfile.yml`, `Taskfile.yaml`, and variants with task commands/includes: https://man7.org/linux/man-pages/man1/make.1.html and https://taskfile.dev/docs/guide. They are good LLM triage inputs and poor deterministic workload classifiers.

## Recommendations

Minimum v1 packs: Universal scanner, Dockerfile, Compose, Kubernetes manifest, Helm, Kustomize, GitHub Actions, Maven, Gradle, npm/Yarn/pnpm, Python pyproject/pip/uv/Poetry, FastAPI/Django/Celery hints, Go modules, .NET project/config, Rails/Laravel, and Cargo. Add a lightweight platform-hints pack for Procfile, Fly, Railway, Render, Cloud Foundry, Serverless, Nx, Makefile, and Taskfile.

Promotion criteria: promote an LLM-discovered hint only when it recurs in real repositories, has an official owner source, produces stable path/line facts, lowers AI file-reading cost, has low false-positive risk, and can be covered by fixtures. Promotion should add evidence extraction only, not semantic conclusions.

Tests and fixtures: include one fixture per ecosystem for manifest parsing, one monorepo fixture per workspace mechanism, one conflict fixture such as npm/yarn lock coexistence, one no-Dockerfile fixture, one Kustomize optional-overlay fixture, one platform-config fixture, and one invalid-citation verifier fixture. The local corpus indicates verifier tests are as important as extractor tests because output contract failures occurred even when service identity was correct (`validation/skill-coverage-validation-2026-07-23.md`).

Anti-goals: do not infer production readiness from package dependencies alone; do not treat Docker Compose as production by default; do not turn cloud-specific config into Kubernetes resources; do not emit registry names, resource limits, security policies, HPA, PDB, or NetworkPolicy defaults not present in the repository; do not execute repository scripts during static analysis.

## Open Questions

- Should the first implementation prioritize broad language packs or the deterministic verifier that catches invalid citations and schema drift?
- Should platform configs such as `fly.toml`, `render.yaml`, and `Procfile` be included in v1 as generic deployment hints or delayed until a platform-pack abstraction exists?
- What corpus size is enough before promoting an LLM-discovered hint into a maintained extractor?
